# PasswordVault：雲端同步規劃

**狀態：規劃階段第一輪已完成（架構骨幹定案，具體數字參數與 API 細節尚待下一輪）**——這份文件記錄的是決策與理由，不是實作步驟；動工前如果規劃有調整，先改這份文件，不要邊做邊讓實作偷偷偏離這裡的定義。

## 1. 背景

`PasswordVault` 現況是純本機應用程式：憑證存在本機一份 `credentials.json`，沒有任何網路服務，天生不支援跨裝置使用同一份密碼庫。這輪規劃的目標是新增一個可選的雲端同步能力，讓同一個使用者能在多台裝置間共用同一份密碼庫——同時維持這個專案一直強調的「沒有後門、開發者也解不開」設計原則（見 `installer/passwordvault_installer.json` 的 EULA 文字）。

這是一個新的、規模不小的子系統，跟現有「單機、零網路」的 `PasswordVault.Core`／`PasswordVault.App` 是加法關係，不是取代——本機單機模式繼續是預設、完整可用的使用方式，雲端同步是選配的加值功能。

## 2. 零知識架構：帳號密碼與主密碼徹底分離

**核心決策**：伺服器驗證用的「帳號密碼」跟本機解密用的「主密碼」是兩個完全獨立、互不相通的東西，不能共用同一組密碼或由同一組密碼推導。

- **帳號密碼**：標準登入用途，伺服器存雜湊（Argon2id）、可以做「忘記密碼」重設流程——因為它只用來證明「你是誰」，不會被拿去解密任何內容。
- **主密碼**：純本機用途，衍生金鑰、解密密碼庫內容，伺服器全程看不到、也驗證不了。忘記主密碼一樣救不回來（跟現有單機版行為一致，這條防線不因為加了雲端同步而放寬）。

這個分離是整個雲端同步設計最重要的一條線——後面所有決策（同步協定、儲存內容、API 設計）都要服從這條原則：**伺服器只能存放/搬移「加密過的內容」，不能存放/推導出任何能解密內容的東西**。

## 3. 後端技術選型：TypeScript，可攜式設計

**決策：後端不留在 .NET 生態系，改用 TypeScript／Node.js 撰寫，且設計成能同時部署在 Cloudflare Workers 跟一般自架伺服器（VM／容器）兩種環境。**

背景考量（詳見 grilling 對話紀錄，摘要如下）：

- 這個後端本身工作範圍刻意設計得很單薄（帳號驗證、存取加密過的 blob、擋異常流量），不做真正的加解密運算——那些邏輯依照第 2 節的零知識原則，全部留在客戶端。這種「工作量輕、但要應付大量零散請求」的場景，跟 serverless edge 平台（Cloudflare Workers）的特性天生契合：沒有一台伺服器可以被壓垮（每個請求獨立、自動水平擴展），Cloudflare 網路本身內建 DDoS 防護，維運負擔幾乎是零——這對「防止伺服器崩掉或效能崩掉」這個明確排在最優先的需求，是架構層級解決，不是靠後續調校。
- 這個 repo 是公開在 GitHub 上的，會有其他人不透過 Cloudflare、自己架設的情境——後端不能只能在 Cloudflare 上跑，語言/框架要能兩邊通吃。TypeScript／Node.js 在這三個候選（TypeScript／Rust／Python）裡「兩邊都能跑」的支援度最好：Cloudflare Workers 原生支援，同一份程式碼也能包成普通 Node.js 伺服器讓自架的人直接跑。Rust 理論上也兩邊都能跑（Workers 上編譯成 WASM，自架編成執行檔），但要維護兩套編譯目標，複雜度高很多；Python 在 Cloudflare Workers 上目前只有實驗性支援，直接排除。
- Rust 的效能／記憶體安全優勢，在這種刻意設計成輕量、非運算密集的後端上發揮不出來太多；真正的資料安全防線是零知識架構本身（伺服器看不到明文），不是「用什麼語言寫伺服器」。

## 4. 儲存層抽象介面

**決策：資料儲存那一層抽成一個介面，不寫死呼叫 Cloudflare 專屬服務。**

- **Cloudflare 部署版**：接 Cloudflare D1（SQLite-based，跟 Workers 同生態系，設定最簡單）。
- **自架參考實作**：接 PostgreSQL——自架情境比較常見、成熟穩定、水平擴展跟備份的工具鏈都很多，比自架 SQLite 更適合「多人同時使用」的場景（SQLite 是單檔案，寫入時容易互相卡住，不適合真的有很多使用者同時寫入的自架場景）。
- 兩邊各自接最適合自己情境的資料庫，同一份業務邏輯程式碼不用因為部署環境不同而分岔維護。

## 5. 帳號系統

- **登入方式**：Email 或使用者代號（擇一即可查到帳號）+ 帳號密碼，這是 v1 範圍。OAuth（Google／GitHub 登入）評估後**不排除但不放進 v1**——這個產品定位是隱私優先的密碼管理工具，把身分綁定第三方帳號對重視隱私的使用者可能是扣分項，且多一個對外部服務的依賴，先做最基本可控的版本，之後有需求再加。
- **TOTP 二階段驗證**：標準 RFC 6238 協定，使用者要用 Google Authenticator 或自己密碼庫裡存的 TOTP 產生器都可以——伺服器只認一組標準演算法算出來的 6 位數字，不管是哪個 App 生成的，這件事不需要額外工程，只是確認伺服器端要支援標準 TOTP 驗證。
- **帳號密碼雜湊演算法**：Argon2id——跟客戶端衍生主密碼金鑰用的是同一個演算法家族，參數調校經驗可以互通，也是目前 OWASP 建議的預設選擇。
- **登入憑證機制**：JWT（伺服器簽章過的 token），不是伺服器端 session 儲存——因為要兩邊通吃（Cloudflare Workers／自架伺服器都能跑），JWT 不需要伺服器另外存一份「誰登入了」的狀態，不管是無狀態的 edge 環境還是自架的多台機器，都不需要額外設計「session 要共用儲存」這件事。

## 6. 新裝置導入（v1 簡單版）

**v1 範圍**：新裝置登入帳號後，要求使用者在該裝置上重新手動輸入一次主密碼，才能本機衍生金鑰、解密同步下來的內容。伺服器全程不參與這個環節（本來就看不到主密碼）。

裝置確認／已登入裝置核准新裝置／QR Code 安全配對這一整套更方便但工程量更大的流程，**列入未來功能，不放進這輪**（見第 9 節）——先把帳號系統、零知識同步這個核心骨架做穩，體驗優化留到核心穩定之後再加。

## 7. 同步機制：逐筆同步 + 時間戳記決勝

**決策：不是整包密碼庫一次全部上傳/下載覆蓋，而是逐筆憑證同步，衝突時比較 `updatedAtUtc`，新的蓋掉舊的。**

現有資料格式（每筆憑證都有自己的 `id`／`createdAtUtc`／`updatedAtUtc`）剛好適合這個做法：兩台裝置各自改不同筆憑證完全不會互相干擾；真的兩台裝置「同時改同一筆」這種罕見情況，就是單純比時間戳記、晚的贏，不做更複雜的合併邏輯（例如 CRDT）。這種複雜度對一個密碼管理工具的實際使用情境（同一使用者很少真的同時在兩台裝置編輯同一筆密碼）不成比例，先簡單堪用，之後發現這個假設不成立再回頭升級。

## 8. 安全防護

- **帳號登入暴力破解防護**：比照現有 `LockoutTracker`（本機主密碼驗證失敗次數限制）同一套精神，搬到伺服器端——同一個帳號連續打錯密碼幾次之後鎖一段時間才能再試，時間隨失敗次數遞增。這是應用層邏輯，寫在後端程式碼裡，不管部署在 Cloudflare 還是自架都一樣生效。
- **一般 API 請求頻率限制**：伺服器程式碼自己要有一層「同一個 IP/帳號短時間內打太多次就先擋一下」的邏輯（自架的人不管有沒有前面加 Cloudflare 都有基本防護）；部署在 Cloudflare 上的話，可以**額外**疊加 Cloudflare 內建的邊緣層流量規則當加分項，但不能只依賴這個。
- **錯誤回應不洩漏內部實作細節**：API 回傳錯誤時，不把資料庫錯誤訊息、程式內部路徑、技術棧細節原封不動吐給前端看，防止攻擊者從錯誤訊息反推系統架構。
- **「只接受官方 PasswordVault 呼叫」這個目標評估後不做**：桌面軟體的用戶端沒有辦法可靠地藏住任何識別碼／金鑰（反組譯就挖得出來），這是通用的資安限制，不是這個專案特有的坑；手機平台有 App 完整性驗證等對應機制，桌面軟體沒有可靠對應手段。做這件事只會給假的安全感。真正有效的防線是：沒有合法帳號登入 token 就完全拿不到任何東西（第 5 節）、加上速率限制/鎖定機制（本節前兩點）——這兩層才是實質擋住濫用的關鍵，不是靠「辨認呼叫端是不是官方 App」。

## 9. 已知會延後或不做的事

- **裝置確認／新裝置核准流程／QR Code 安全配對**：見第 6 節，v1 用簡單版（重新輸入主密碼），這一套更完整的體驗留到之後有需求時再單獨規劃。
- **OAuth 第三方登入**：見第 5 節，不排除，但不在這輪範圍內。
- **API 用戶端身分辨識（例如版本標頭檢查）**：見第 8 節，評估後判斷投資報酬率不高，先不做。

## 10. 尚待規劃的細節

以下留到下一輪 grilling 繼續定案，本輪只先寫下已知要問的問題，不猜答案：

- 帳號鎖定機制的具體門檻值（連續錯幾次觸發鎖定、鎖多久、遞增規則的具體公式）。
- API 速率限制的具體數字（每個 IP/帳號每分鐘/每小時允許幾次請求）。
- JWT token 的有效期限、要不要搭配 refresh token 機制。
- 具體的 API 端點清單與請求/回應格式（登入、同步上傳/下載、裝置管理等）。
- 資料庫的實際 schema 設計（帳號表、裝置表、加密內容表的欄位）。
- 自架版的部署方式（Docker image？裸執行檔？）與設定檔格式。
- 前端（`PasswordVault.App`／`PasswordVault.Web`）要新增哪些 UI（登入頁、雲端同步開關、裝置管理頁面等）——這輪只定了後端骨幹，前端 UI 完全還沒規劃。
