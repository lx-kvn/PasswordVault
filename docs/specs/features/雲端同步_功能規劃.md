# PasswordVault：雲端同步規劃

**狀態：規劃階段第一輪已完成（架構骨幹定案，具體數字參數與 API 細節尚待下一輪）**——這份文件記錄的是決策與理由，不是實作步驟；動工前如果規劃有調整，先改這份文件，不要邊做邊讓實作偷偷偏離這裡的定義。

## 1. 背景

`PasswordVault` 現況是純本機應用程式：憑證存在本機一份 `credentials.json`，沒有任何網路服務，天生不支援跨裝置使用同一份密碼庫。這輪規劃的目標是新增一個可選的雲端同步能力，讓同一個使用者能在多台裝置間共用同一份密碼庫——同時維持這個專案一直強調的「沒有後門、開發者也解不開」設計原則（見 `installer/passwordvault_installer.json` 的 EULA 文字）。

這是一個新的、規模不小的子系統，跟現有「單機、零網路」的 `PasswordVault.Core`／`PasswordVault.App` 是加法關係，不是取代——本機單機模式繼續是預設、完整可用的使用方式，雲端同步是選配的加值功能。

## 2. 零知識架構：帳號密碼與主密碼徹底分離

**核心決策**：伺服器驗證用的「帳號密碼」跟本機解密用的「主密碼」是兩個完全獨立、互不相通的東西，不能共用同一組密碼或由同一組密碼推導。

- **帳號密碼**：標準登入用途，伺服器存雜湊（Argon2id）、可以做「忘記密碼」重設流程——因為它只用來證明「你是誰」，不會被拿去解密任何內容。
- **主密碼**：純本機用途，衍生金鑰、解密密碼庫內容，伺服器全程看不到、也驗證不了。忘記主密碼一樣救不回來（跟現有單機版行為一致，這條防線不因為加了雲端同步而放寬）。

這個分離是整個雲端同步設計最重要的一條線——後面所有決策（同步協定、儲存內容、API 設計）都要服從這條原則：**伺服器只能存放/搬移「加密過的內容」，不能存放/推導出任何能解密內容的東西**。

## 3. 後端技術選型：TypeScript，可攜式設計

**決策：後端不留在 .NET 生態系，改用 TypeScript／Node.js 撰寫，且設計成能同時部署在 Cloudflare Workers 跟一般自架伺服器（VM／容器）兩種環境。**

背景考量（詳見 grilling 對話紀錄，摘要如下）：

- 這個後端本身工作範圍刻意設計得很單薄（帳號驗證、存取加密過的 blob、擋異常流量），不做真正的加解密運算——那些邏輯依照第 2 節的零知識原則，全部留在客戶端。這種「工作量輕、但要應付大量零散請求」的場景，跟 serverless edge 平台（Cloudflare Workers）的特性天生契合：沒有一台伺服器可以被壓垮（每個請求獨立、自動水平擴展），Cloudflare 網路本身內建 DDoS 防護，維運負擔幾乎是零——這對「防止伺服器崩掉或效能崩掉」這個明確排在最優先的需求，是架構層級解決，不是靠後續調校。
- 這個 repo 是公開在 GitHub 上的，會有其他人不透過 Cloudflare、自己架設的情境——後端不能只能在 Cloudflare 上跑，語言/框架要能兩邊通吃。TypeScript／Node.js 在這三個候選（TypeScript／Rust／Python）裡「兩邊都能跑」的支援度最好：Cloudflare Workers 原生支援，同一份程式碼也能包成普通 Node.js 伺服器讓自架的人直接跑。Rust 理論上也兩邊都能跑（Workers 上編譯成 WASM，自架編成執行檔），但要維護兩套編譯目標，複雜度高很多；Python 在 Cloudflare Workers 上目前只有實驗性支援，直接排除。
- Rust 的效能／記憶體安全優勢，在這種刻意設計成輕量、非運算密集的後端上發揮不出來太多；真正的資料安全防線是零知識架構本身（伺服器看不到明文），不是「用什麼語言寫伺服器」。

## 4. 儲存層抽象介面

**決策：資料儲存那一層抽成一個介面，不寫死呼叫 Cloudflare 專屬服務。**

- **Cloudflare 部署版**：接 Cloudflare D1（SQLite-based，跟 Workers 同生態系，設定最簡單）。
- **自架參考實作**：接 PostgreSQL——自架情境比較常見、成熟穩定、水平擴展跟備份的工具鏈都很多，比自架 SQLite 更適合「多人同時使用」的場景（SQLite 是單檔案，寫入時容易互相卡住，不適合真的有很多使用者同時寫入的自架場景）。
- 兩邊各自接最適合自己情境的資料庫，同一份業務邏輯程式碼不用因為部署環境不同而分岔維護。

## 4.1 自架部署方式：Docker image，設定用環境變數

**決策：自架版只發布 Docker image（搭配 docker-compose 範例，把後端服務跟 PostgreSQL 綁在一起），不另外維護裸執行檔版本；設定用環境變數，不是自訂設定檔格式。**

- Docker 是現在自架軟體事實上的標準做法——最接近的真實案例是 Vaultwarden（相容 Bitwarden 協定的自架密碼管理伺服器），就是純 Docker 發布，沒有另外出裸執行檔。使用者裝好 Docker、抓我們發布好的 image、填幾個環境變數（資料庫連線字串、JWT 簽章密鑰、Resend API 金鑰、寄件網域等）就能跑起來，不用自己處理 Node.js 版本、相依套件這些環境問題。
- 幫 Windows/Mac/Linux 各自打包裸執行檔是額外工程負擔，Docker 已經解決「不管系統是什麼都跑得起來」這個問題，兩套並存是重複造輪子。
- 環境變數是 Docker／12-factor app 的標準慣例，Cloudflare Workers 那邊本來就是用環境變數/密鑰綁定的方式設定，兩邊用同一套設定思維，不用為自架另外設計一套設定檔格式。

## 5. 帳號系統

- **登入方式**：Email 或使用者代號（擇一即可查到帳號）+ 帳號密碼，這是 v1 範圍。OAuth（Google／GitHub 登入）評估後**不排除但不放進 v1**——這個產品定位是隱私優先的密碼管理工具，把身分綁定第三方帳號對重視隱私的使用者可能是扣分項，且多一個對外部服務的依賴，先做最基本可控的版本，之後有需求再加。
- **TOTP 二階段驗證**：標準 RFC 6238 協定，使用者要用 Google Authenticator 或自己密碼庫裡存的 TOTP 產生器都可以——伺服器只認一組標準演算法算出來的 6 位數字，不管是哪個 App 生成的，這件事不需要額外工程，只是確認伺服器端要支援標準 TOTP 驗證。
- **帳號密碼雜湊演算法**：Argon2id——跟客戶端衍生主密碼金鑰用的是同一個演算法家族，參數調校經驗可以互通，也是目前 OWASP 建議的預設選擇。
- **登入憑證機制**：JWT（伺服器簽章過的 token），不是伺服器端 session 儲存——因為要兩邊通吃（Cloudflare Workers／自架伺服器都能跑），JWT 不需要伺服器另外存一份「誰登入了」的狀態，不管是無狀態的 edge 環境還是自架的多台機器，都不需要額外設計「session 要共用儲存」這件事。
  - **Access token 效期 15 分鐘，搭配效期 30 天的 refresh token**：access token 是實際打 API 用的短命憑證，外洩了能被濫用的時間窗很短；refresh token 存在裝置本機，effective 期間內可以默默換發新的 access token，使用者不用每 15 分鐘重新輸入一次帳號密碼，30 天內都不用重新登入。
  - **refresh token 綁定裝置，且每次用掉就輪替成新的一張、作廢舊的**：如果偵測到一張已經被輪替掉的舊 refresh token 又被拿出來用，代表這張 token 外洩了，可以直接撤銷整個裝置的存取權。這跟裝置管理清單（第 6 節）接得上——從裝置清單移除一台裝置，就是撤銷它的 refresh token。
- **登入暴力破解防護：鎖「帳號＋來源 IP」的組合，不是單鎖帳號本身**——單鎖帳號的話，攻擊者只要知道使用者的 email，故意連續打錯密碼就能把使用者自己鎖在外面，變成一種拒絕服務攻擊。鎖「帳號＋IP」組合，使用者從其他正常 IP（家裡、公司）登入不受影響。門檻值沿用現有 `LockoutTracker`（`src/PasswordVault.Core/Security/LockoutTracker.cs`）的既有數字：連續錯 5 次觸發鎖定，鎖定時間從 30 秒起跳、每次翻倍（30/60/120/…），上限 3600 秒（1 小時），驗證成功歸零。
- **二次驗證（2FA）是可選的，不強制**：設定頁可以個別開啟 TOTP、Email 驗證碼，兩個都開也可以；登入時只要滿足其中一種已開啟的方式就算通過，不是兩者都要驗證。**Email 驗證碼永遠是保底手段，不能真的完全關閉**——只開 TOTP、沒有任何保底救援手段的話，弄丟 TOTP 裝置就真的登不進帳號；Email 保底讓「弄丟 TOTP 裝置」不等於「帳號回不去了」，同時不用另外設計一次性備援代碼機制。
- **新裝置／鎖定觸發時寄信通知使用者**：(1) 從沒見過的新裝置成功登入時寄信；(2) 登入鎖定機制被觸發時立刻寄信——這兩種情況才寄，不是每次登入都寄，避免使用者被信件轟炸到麻木。「認得哪些裝置」這份清單本來就是裝置管理功能（第 6 節、未來功能的裝置確認也會用到）的一部分，不是額外多開一條資訊基礎設施。
- **忘記帳號密碼可以寄信重設，但這只救得回帳號本身，救不回密碼庫內容**——帳號密碼跟主密碼是兩回事（見第 2 節），重設帳號密碼只是讓使用者重新登入、看得到裝置清單等帳號層級的東西；密碼庫實際憑證在伺服器上是用「主密碼衍生金鑰」加密的，主密碼沒找回來，重設帳號密碼救不了這些內容。**「忘記密碼」流程的 UI 文案要非常明確講清楚這個區別**，這是密碼管理器產業真實出過事故的地方（使用者誤以為重設密碼＝找回密碼庫）。
- **忘記主密碼的補救管道，沿用既有的恢復金鑰／Passkey 解鎖機制，不另外設計**：現有產品「密碼／Passkey／恢復金鑰」三種互相獨立解鎖方式，本來就是為了「忘記密碼」這個情境存在——只要使用者當初有設定恢復金鑰或 Passkey 任一個，忘記主密碼一樣解得開。**技術要求**：同步到伺服器的加密內容，要維持「同一把主金鑰，分別被密碼／Passkey／恢復金鑰各自包一份」的既有結構，不能因為雲端同步而簡化成只認密碼。**UI 待辦**：啟用雲端同步時，應更明確提醒／鼓勵使用者設定恢復金鑰——雲端帳號完全沒有任何救援手段的風險比單機版更高（單機弄丟頂多丟一台裝置的資料，雲端帳號弄丟就是所有裝置都進不去）。

## 6. 新裝置導入（v1 簡單版）

**v1 範圍**：新裝置登入帳號後，要求使用者在該裝置上重新手動輸入一次主密碼，才能本機衍生金鑰、解密同步下來的內容。伺服器全程不參與這個環節（本來就看不到主密碼）。

裝置確認／已登入裝置核准新裝置／QR Code 安全配對這一整套更方便但工程量更大的流程，**列入未來功能，不放進這輪**（見第 9 節）——先把帳號系統、零知識同步這個核心骨架做穩，體驗優化留到核心穩定之後再加。

## 6.1 多支 Passkey ＋跨平台（WebAuthn）

**決策：一支帳戶可以註冊多支 Passkey，且要真正跨平台（Windows／Mac／手機／實體金鑰皆可），不是只顧 Windows。**

現有 Passkey 實作直接呼叫 Windows 專屬的 `KeyCredentialManager`（Windows Hello），且資料結構裡只有單一個 `PasskeyWrappedMasterKeyBase64` 欄位（因為現有單機版本來就只在一台裝置上用）。這輪決定：

- **資料結構**：Passkey 欄位從「單一個」改成「一份清單」，每一支 Passkey 各自獨立包一份同樣那把主金鑰（跟密碼／恢復金鑰各自包一份的既有設計同一個精神）。新增一支 Passkey 的流程：這台裝置先用其他方式（密碼／既有的另一支 Passkey／恢復金鑰）解鎖拿到主金鑰，再用這台裝置的 Passkey 把同一把主金鑰重新包一份、只把包過的密文傳上伺服器——主金鑰本身不離開裝置。
- **平台層面：從 `KeyCredentialManager` 換成標準 WebAuthn 協定**——Windows Hello、Touch ID、Android 生物辨識、實體金鑰（YubiKey 等）都是透過同一套 WebAuthn 跟伺服器溝通，只是各自的認證器不同，這是真正跨平台 Passkey 的唯一可行做法。
- **好消息：客戶端不需要另外寫平台專屬程式碼**——`PasswordVault.App`（以及未來可能的 Mac 版）都是用瀏覽器引擎（WebView2／WKWebView）顯示畫面，WebAuthn 是瀏覽器標準 API（`navigator.credentials`），前端 Vue 直接呼叫就會自動路由到該平台的認證器，不用為每個平台各寫一套原生 Passkey 程式碼。
- **真正要新蓋的工程在伺服器端**：要實作 WebAuthn 的「信賴方（Relying Party）」註冊/驗證挑戰流程——這是一套有規範的協定（挑戰值產生、attestation 驗證等），不是隨便包一個 API 就好，是這輪範圍裡工程量較大的一塊，但因為使用者明確表示跨平台是雲端同步的核心目的（做雲端同步就是為了不被綁在單一平台），這塊正式列入 v1 範圍，不放進未來功能清單。

## 7. 同步機制：逐筆同步 + 時間戳記決勝

**決策：不是整包密碼庫一次全部上傳/下載覆蓋，而是逐筆憑證同步，衝突時比較 `updatedAtUtc`，新的蓋掉舊的。**

現有資料格式（每筆憑證都有自己的 `id`／`createdAtUtc`／`updatedAtUtc`）剛好適合這個做法：兩台裝置各自改不同筆憑證完全不會互相干擾；真的兩台裝置「同時改同一筆」這種罕見情況，就是單純比時間戳記、晚的贏，不做更複雜的合併邏輯（例如 CRDT）。這種複雜度對一個密碼管理工具的實際使用情境（同一使用者很少真的同時在兩台裝置編輯同一筆密碼）不成比例，先簡單堪用，之後發現這個假設不成立再回頭升級。

## 8. 安全防護

- **帳號登入暴力破解防護**：比照現有 `LockoutTracker`（本機主密碼驗證失敗次數限制）同一套精神，搬到伺服器端——同一個帳號連續打錯密碼幾次之後鎖一段時間才能再試，時間隨失敗次數遞增。這是應用層邏輯，寫在後端程式碼裡，不管部署在 Cloudflare 還是自架都一樣生效。
- **一般 API 請求頻率限制**：伺服器程式碼自己要有一層「同一個 IP/帳號短時間內打太多次就先擋一下」的邏輯（自架的人不管有沒有前面加 Cloudflare 都有基本防護）；部署在 Cloudflare 上的話，可以**額外**疊加 Cloudflare 內建的邊緣層流量規則當加分項，但不能只依賴這個。不同端點分開設定門檻，不用同一個數字：
  - 登入端點：每個 IP 每分鐘最多 10 次（不分帳號，防止對大量不同帳號亂槍打鳥），是鎖定機制（鎖帳號+IP）之外再疊一層粗防護網。
  - 同步端點（上傳/下載憑證）：每個帳號每分鐘最多 60 次——留寬一點，因為多裝置正常編輯時本來就會頻繁觸發同步。
  - 其他一般 API（裝置管理、帳號設定等）：每個帳號每分鐘最多 100 次，當保底防線。
  - 這幾個數字是先抓合理起點，不是精算出的最佳值，上線後依實際流量觀察再調整，不寫死成程式碼常數以外拿不到的值。
- **錯誤回應不洩漏內部實作細節**：API 回傳錯誤時，不把資料庫錯誤訊息、程式內部路徑、技術棧細節原封不動吐給前端看，防止攻擊者從錯誤訊息反推系統架構。
- **「只接受官方 PasswordVault 呼叫」這個目標評估後不做**：桌面軟體的用戶端沒有辦法可靠地藏住任何識別碼／金鑰（反組譯就挖得出來），這是通用的資安限制，不是這個專案特有的坑；手機平台有 App 完整性驗證等對應機制，桌面軟體沒有可靠對應手段。做這件事只會給假的安全感。真正有效的防線是：沒有合法帳號登入 token 就完全拿不到任何東西（第 5 節）、加上速率限制/鎖定機制（本節前兩點）——這兩層才是實質擋住濫用的關鍵，不是靠「辨認呼叫端是不是官方 App」。

## 9. 已知會延後或不做的事

- **裝置確認／新裝置核准流程／QR Code 安全配對**：見第 6 節，v1 用簡單版（重新輸入主密碼），這一套更完整的體驗留到之後有需求時再單獨規劃。
- **OAuth 第三方登入**：見第 5 節，不排除，但不在這輪範圍內。
- **API 用戶端身分辨識（例如版本標頭檢查）**：見第 8 節，評估後判斷投資報酬率不高，先不做。
- **網頁版金庫（伺服器直接提供瀏覽器可用的 GUI，不透過桌面 App）**：v1 伺服器只當純 API 用，只有桌面版（未來可能還有行動版）App 會呼叫。網頁版能一併解決「沒裝 App 的裝置臨時使用」與「情境 B 跨平台」需求，`packages/password-locker-ui` 這個共用元件理論上也能重用（換一組打雲端 API 的 `sendMessage`/`requestMessage` 實作），但主密碼衍生金鑰運算要搬進瀏覽器執行，攻擊面（惡意瀏覽器擴充功能、XSS）跟原生桌面 App 完全不同，值得之後單獨開一輪仔細規劃安全性，不跟這輪的核心骨架綁在一起趕工。

## 10. 尚待規劃的細節

以下留到下一輪 grilling 繼續定案，本輪只先寫下已知要問的問題，不猜答案：

- WebAuthn 挑戰值／attestation 驗證的具體實作細節，以及 Relying Party ID／origin 設定（自架情境下網域不固定，這裡要特別注意）。
- 具體的 API 端點清單與請求/回應格式（登入、二次驗證、Passkey 註冊/驗證、同步上傳/下載、裝置管理等）。
- **寄信服務：定案用 Resend 當預設實作，抽成介面讓自架的人可以換成別的服務（SendGrid／SES／自己的 SMTP）**——Cloudflare 沒有自己的交易信寄送產品（Email Workers 是收信/轉信用的，不是寄送用途），不管部署在哪裡都要接第三方寄信 API，Resend 的 TypeScript 生態系友善、免費額度（每月 3000 封）適合起步階段規模。
  - **寄件網域**：不能寫死在程式碼裡，是每個部署各自的設定值（自架的人要用自己擁有的網域）；正式上線前需要網域擁有者自己在 DNS 加 SPF/DKIM/DMARC 紀錄。開發/測試階段可以先用 Resend 提供的共用測試網域頂著。
  - **選網域的原則**：優先選信譽較好的 TLD（`.com`／`.org`／`.dev` 這類，避免 `.win` 這種常被拿去發垃圾信、容易被過濾機制降評的冷門 TLD），且名稱盡量貼近品牌「PasswordVault」，讓使用者收到信能一眼看出寄件者跟自己在用的軟體有關聯——不只是技術上能寄出去，使用者辨識真偽的信任感也要顧到。這個網域買了之後，除了拿來寄信，也可以順便當作這個專案未來的正式對外網域（API 網址、之後可能的網頁版首頁），不用只當一次性的寄信專用網域。
- 資料庫的實際 schema 設計（帳號表、裝置表、Passkey 清單表、加密內容表的欄位）。
- 前端（`PasswordVault.App`／`PasswordVault.Web`）要新增哪些 UI（登入頁、二次驗證設定、Passkey 管理、雲端同步開關、裝置管理頁面等）——這輪只定了後端骨幹，前端 UI 完全還沒規劃。
